一句話

在店裡既有的監視器上，加一層不用 AI 模型的影像算法整天守著；有可疑狀況時，才叫醒關在沙箱裡的 Nemotron Agent，讓它查 POS、查現場訊號，再決定要不要通知人。

它盯的是「客人有沒有被照顧到」，不是「哪個員工在偷懶」。老闆接到客訴時，也可以打一句話問它，它會從一整天的紀錄裡找出那一刻。

整套系統 10-21 在主辦現場的 DGX Spark 上裝好、跑通：模型、沙箱、即時判定、看片網頁都在這台機器上。

三條路

  1. 回查層：常駐層在吧台畫面上找到候選（客人在結帳區超過 30 秒、收銀機前沒有店員），把候選的描述交給回查層 Agent。Agent 呼叫工具查 POS、桌況、現場訊號，最後經 notify 選一個固定句型和分級。提醒先過護欄，再分級。決賽 demo 用 9/13 那段的加密影格，傳進沙箱裡跑。
  2. 每日摘要：在錄影主機上每天跑一次，產出一天的事件、候選、收桌、POS 和遮過頭的縮圖。看片網頁的日曆和單日頁、客訴 agent 的查詢，都讀這份摘要。客訴 agent 不碰影格，也不需要金鑰。
  3. 即時：現場 Spark 每 2 秒從錄影主機拉一次新的加密影格（只能唯讀拉取），在沒有網路的容器裡解開、判定。滿 30 秒、收銀機前沒有店員，就跳一行警示。警示是規則判的，不經模型。

資料不落地：哪些離開、哪些不離開

結論：原始影格在硬碟上只有密文，解密金鑰不寫在任何一台 Spark 的硬碟上。模型和工具只拿到數字和時刻。但網頁上的照片是遮過頭的明文 JPEG，遮臉會漏，所以網頁一定要登入、有期限。

東西存在哪裡、什麼形式會不會離開
原始影格錄影主機的硬碟上，每張都是加密檔（AES-GCM，每張一個隨機數）。讀的時候在記憶體裡解開，解開的畫面不寫回硬碟即時那條路會把加密影格拉到現場 Spark，到了那裡仍是密文，只在無網路容器的記憶體裡解開
解密金鑰不寫在任何一台 Spark 的硬碟上。從店家這一方的筆電經標準輸入送進程式，只在程式的記憶體裡只進錄影程式、即時判定容器、沙箱裡的回查層 demo
每日摘要數字（事件、候選、收桌、POS 對照）加處理過的縮圖這是離開錄影主機的主要東西，送到現場 Spark 給網頁和客訴 agent
網頁上的照片和即時畫面人頭貼了青蛙的明文 JPEG登入的人看得到。網頁每個請求都要帳密，過了期限整個網頁回 403
沒遮的縮圖為了做遮臉，從錄影主機直接串流到店家這一方的筆電，在那台筆電上處理兩台 Spark 都不落地；不放上網頁
模型看到的只有工具回傳的數字、時刻和文字。工具不回影像模型和兩個 Agent 都在零外部端點的沙箱裡
即時判定在 --network none 的容器裡這個容器根本沒有網路介面

邊界：我們不說的話

下面這幾句我們不說，因為它們不成立：

  • 「沒有任何影像離開」：網頁有遮過頭的縮圖和即時畫面。
  • 「所有照片都已遮臉」「已去識別化」：青蛙會漏。9/20 那組照片裡就有清楚的臉沒遮到。
  • 「機器上的照片都已加密」：只有原始影格是加密的，縮圖和即時畫面是明文。
  • 「資料只在店內這台機器上」：見下面這一條。

開發期的錄影主機是一台借來的 DGX Spark，放在店外的機房，不在店裡。影格從店裡的監視器主機取來，加密後才寫進它的硬碟。設計上這台應該放在店裡；這一步還沒有在店內實裝。加密防的是有人翻硬碟，防不了有人在程式執行時讀記憶體。

為什麼放在邊緣、為什麼舊設備就夠

為什麼放在邊緣

理由性質說明
隱私前提畫面裡有客人和員工的臉。原始影像一旦送上雲端，就是個資風險
斷網前提小店網路不穩。斷網時警示和紀錄不能停
即時需求碗盤沒收、客人在櫃台沒人理，晚十分鐘才知道就沒用了。即時警示延遲 1–2 秒
推理放店內我們的選擇回查層只看文字，技術上可以上雲。我們選在地：POS 營運數據同樣不該離店；不受外部服務影響

延續舊設備就能用

結論：不換攝影機、不加感測器。常駐層只要每秒兩三張低解析度畫面，用很少的運算。

  • 直接接店裡現有的監視器主機（DVR）。它沒有開串流，所以每 0.4 秒向它的快照網址要一張 JPEG，352×240 像素，四路各每秒 2.5 張。快照也省掉了影片解碼。
  • 常駐層不用 AI 模型，是實測後的選擇。我們先試了 NVIDIA 的 PeopleNet 人物偵測模型：俯拍角度下不可靠（空桌也有 0.146 的底噪），而且四路跑 CPU 時每路只有每秒 1 張，跟不上取流。改用不需要人物偵測的影像算法之後：

客訴 agent 與規則試玩

結論：日期、時段、客訴類型用規則判，不交給模型。模型只決定查哪幾樣、怎麼寫結論。它在沙箱裡，只有四個唯讀的查詢工具，加上寫軌跡的 audit。

為什麼用規則判

  • 日期：模型會編時間。查錯一天就整個答錯，而這一步規則就做得到。抓不到日期就請老闆補。
  • 類型決定查法：糾紛（態度、集點、付款）要找「客人在櫃台待最久」，等待要找「收銀機前沒有店員」，桌子沒收要查桌況。「結帳時很兇」是糾紛，不是等待，所以糾紛先比對。
  • 擋輸入、擋輸出：送進模型前，用正規表示式擋「要求系統做別的事」和離題；回答裡有程式碼就不給老闆看。這是基本款，換個說法還是可能漏。

試試看：規則怎麼判。這段 JavaScript 照程式裡的三條規則（擋輸入、抓日期時段、判類型）逐條改寫，在你的瀏覽器裡跑，不叫模型。

結論的格式

固定三段：【查到的】只能引用工具回傳的時刻和數字；【判斷】；【查不到的】寫出資料看不到的部分（態度、講了什麼、會員、集點、餐點品質）。不指名、不評價任何員工。

已知限制

  1. 模型的判斷不穩定。同一筆候選，重啟後有時不呼叫 notify、只把分級寫在文字裡；分級會在店長和前場之間變。前場是不經人確認就送出的那一級。原因沒有驗證。
  2. 有一種無聲失效還沒攔。模型把 notify 寫成純文字放在結論的結尾，程式只檢查開頭，會當成正常結論收下。
  3. 遮臉會漏。俯拍鏡頭上，抓臉和姿勢模型都不能當隱私保護。所以網頁要登入、有期限，不對外說「已去識別化」。
  4. 結帳區的候選不準。人工核對 10 筆：4 筆候選都不是客人在等（框裡有吧台座位）；6 筆 POS 證實的久候，收銀機前都有店員。所以候選只當線索、由人確認，不直接提醒。
  5. 驗證樣本小。9/20 那則只有 1 筆；客訴 agent 驗過 3 題；回查層的結論對不對，沒有系統性驗證。
  6. 桌況只涵蓋 A、B 兩張四人桌。
  7. 模型寫的文字，只有 notify 的句子過護欄。軌跡和客訴結論只有基本的規則檢查。
  8. 只在一家店、DGX Spark 上驗證過。NVFP4 需要 Blackwell 架構，Orin 這類機器跑不了；Jetson 沒有測過。
  9. 開發期的錄影主機不在店裡（見〈資料不落地〉）。即時警示只顯示在網頁上，沒有接到店裡的裝置。

評審最可能問的問題

點開看答案。答案都照實測和文件，沒驗過的直接說。

為什麼要放在邊緣，不用雲端？

兩個前提和一個選擇。前提一：畫面裡有客人和員工的臉，原始影像送上雲端就是個資風險。前提二：小店網路不穩，斷網時警示和紀錄不能停。選擇：回查層只看文字，技術上可以上雲；我們選在地，因為 POS 營運數據同樣不該離店，也不想受外部服務影響。

這會不會變成監控員工？

系統盯的是「客人有沒有被照顧到」。提醒只能是固定句型，例如「A 桌等很久了，已經 12 分鐘」，沒有自由文字的參數；送出前護欄擋對人的評價和人名。客訴 agent 的結論規定不指名、不評價員工。9/20 的例子裡，系統找出的反而是「店員全程在櫃台、客人卡在集點流程」。

但技術上管好資料，不等於回答了「憑什麼拍」。員工的告知和同意要另外做，不是這套系統能代替的。

遮臉會漏，怎麼辦？

我們承認會漏。試過三種：和空店比、有差就馬賽克（不漏，但畫面糊到看不出狀況）；只抓臉（俯拍鏡頭漏很多）；用姿勢模型找頭（現用，1,491 張貼了 4,106 隻，仍會漏）。所以處理方式是：網頁每個請求都要帳密、過了期限整個關閉；原始影格不放上網頁；對外不說「已去識別化」。

誤報怎麼控制？

靠分級，不靠調門檻。測得準的訊號（碗盤在不在桌上）才准當下提醒；測不準的（結帳區有人，但看不出在做什麼）只列成候選，由人確認。人工核對 10 筆結帳區資料，4 筆候選都不是客人在等，所以候選不直接提醒。模型選了「店長」級，也只會掛起來等人確認。

斷網還能不能用？

能。三種證據：程式攔截所有對外連線、跑完整條鏈路，零次對外連線嘗試；關掉 Wi-Fi 後模型從零啟動約 225 秒，流程照常；即時判定容器本來就沒有網路介面。斷網那次，找候選的部分結果一樣；模型的判斷不同，原因是重啟，不是斷網。

模型多大、多快、吃多少記憶體？

Nemotron Nano 12B v2 VL，NVIDIA 官方 NVFP4-QAD 量化版，模型檔 10.6 GB（BF16 是 26.4 GB），載入 9.95 GiB。8 張畫面一次判斷，中位數 4.34 秒；輸出約 11.6 tokens/秒。模型服務照 24 GB 預算啟動，10-21 佔 19,293 MiB，多數是預留的 KV cache。常駐層不用模型：0.05 核、GPU 0%、334 MB。沒有做剪枝。

Agent 真的有自主決策，還是只是 prompt？

模型自己決定呼叫哪些工具、呼叫幾次、選哪個分級。9/13 那筆，它查完 POS 覺得證據不夠，自己再去查現場訊號。程式負責邊界：工具重複失敗就擋、沒有進展就安全中止、工具呼叫沒被解析就算失敗、句型和分級寫死。

也有該說清楚的地方：日期和客訴類型是規則判的，不是模型；模型的分級重啟後會變，這是目前最大的未解問題。

為什麼要用 NemoClaw 沙箱？

Agent 能呼叫工具，就要限制它能碰到什麼。沙箱讓每一條連線都經政策代理、照白名單放行。出廠的白名單會放行 npm、pypi、huggingface 等，零外部端點是我們收緊後的結果，而且每次重建沙箱都要重新收緊。實測沙箱裡連外部網站全被擋；直連模型服務也是 403，只能走受控推論路徑。

換一家店要做什麼？

不換攝影機：只要店裡的監視器主機有快照網址。要做的是：在畫面上畫區域（桌子、客人區、收銀機前），取一段空店畫面當基準，接上 POS 匯出檔，用那家店的真實素材校準門檻，判準（例如「超過 30 秒算漏接」）由店家定。目前只在一家店驗證過，第二家店還沒做。

成本多少？

我們沒有做價格估算。能說的是運算量：不用換監視器、不加感測器；常駐層只要 0.05 核；模型只在有候選或有客訴時才跑，9/13 一整天只叫醒 7 次。硬體只在 DGX Spark 上驗證過，更小的機器沒有測。

28 秒那個數字是怎麼量的？樣本多少？

9/20 吧台一整天 9.5 小時、71,815 張加密影格，在錄影主機上（不是現場 Spark）跑一次「客人在結帳區連續 120 秒以上」的掃描，28.08 秒交出 4 個時刻，其中一組經店家看畫面確認是那則評論。樣本只有 1 筆，不能說召回率 100%。另外 3 個不是這則客訴。一個月後換一支程式重跑，4 筆數字完全一樣。

同樣的問題，系統每次答得一樣嗎？

不用模型的那一半一樣：換機器、斷網、重啟，抓到的事件和數字一個都沒變。用模型的那一半不一樣：10-21 四次 demo，分級一次店長、一次前場，有兩次沒有呼叫 notify。所以我們把「會不會送出」的權限放在分級規則和人工確認上，不放在模型的文字上。
